# 責任分割ルール

## 目的

- 機能追加で肥大化したコードを、変更しやすく壊れにくい構造へ戻す。
- 1クラス1責務を徹底し、レビュー時に「どこを見ればよいか」を明確にする。

## 適用対象（現時点）

- `game-client/game-logics/phaser/scenes/GridCellsScene.ts`
- `game_server/rust_app/src/application/game/process_turn_usecase.rs`
- `game_server/rust_app/src/domain/triggergame_simulator/models/game/game.rs`
- `game_server/rust_app/src/domain/triggergame_simulator/models/step/step.rs`

---

## 共通原則

1. クラスは「理由が1つだけ」で変更される状態を目指す。
2. I/O（UI操作・DB・WebSocket）とドメイン計算を同じメソッドに混在させない。
3. 入力受付と処理実行を分離する。
4. 副作用（保存・通知）は最後に集約して実行する。
5. 命名で責務を表す。
: `*Controller` はイベント受付、`*Service` は業務処理、`*Repository` は永続化。

## レイヤー境界

- Client Scene層
: Phaserイベント受信、描画オーケストレーションのみ。
- Client Logic層
: 選択・移動・トリガー設定・ターン計画のルールを処理。
- Application層（Server）
: 1ユースケースの手順を組み立てる。計算ロジックは持たない。
- Domain層（Server）
: 不変条件と純粋なゲームルールを保持。
- Infrastructure層（Server）
: DB/API通信など外部依存。

---

## フロントエンド分割ルール（GridCellsScene）

### Sceneに残してよい責務

- `preload/create` の初期化と依存オブジェクトの組み立て。
- 各Controllerへの委譲。

### Sceneから分離する責務

- 入力解釈
: pointer/touchの状態遷移、ドラッグ判定、ピンチ判定。
- 選択・移動判定
: キャラ選択、移動可能セル計算、選択解除。
- トリガー設定
: 扇形表示、角度更新、確定処理。
- ターン計画
: AP消費、Action履歴、送信Step構築。
- ターン再生
: サーバー応答のTurn再生、アニメーション完了管理。

### 推奨分割（例）

- `InputController`
: `createMouseInteraction` から入力解釈を移管。
- `SelectionService`
: `selectCharacter` `showMovableHexes` `clearSelection` を移管。
- `TriggerSettingController`
: `startTriggerSetting` `showTriggerFan` `updateTriggerFan` `completeTriggerSetting` を移管。
- `TurnPlanner`
: `recordActionHistory` `consumeActionPoint` を移管。
- `TurnReplayController`
: `executeTurn` `completeUnitActionPhase` を移管。

### 量的ガードレール

- 1ファイル目安: 400行以下。
- 1メソッド目安: 60行以下。
- 条件分岐のネスト: 3段まで。

## サーバー分割ルール（process_turn_usecase）

### UseCaseに残してよい責務

- ユースケース手順の順序制御。
- トランザクション境界の定義。
- 成功/失敗時の返却方針。

### UseCaseから分離する責務

- 提出受付の検証と保存。
- 対戦相手ターンの待ち合わせ判定。
- ターン解決の計算処理。
- 通知ペイロード組み立て。

### Turn情報推奨分割（例）

- `TurnSubmissionService`
: 重複提出チェック、Turn保存、片側提出時の早期終了。
- `TurnResolutionService`
: 両者Turn取得、`game.turn_start` 呼び出し、保存・通知。
- `TurnNotifier`
: Connection取得とWebSocket送信。

---

## ドメイン分割ルール（Game/Step）

### 集約（Entity）に持たせる責務

- 不変条件の保持。
- 状態遷移の正当性保証。

### 集約から外す責務

- 長い手順処理（複数ループでの計算パイプライン）。
- プレイヤー別投影などの表示向け変換。

### step/gameの推奨分割（例）

- `StepExecutionService`
: `Step::step_start` の「検証・移動・戦闘生成」を分離。
- `VisibilityProjectionService`
: `to_player_step` の視界投影を分離。
- `TurnResolver`（必要時）
: `Game::turn_start` のステップ統合手順を分離。

---

## テスト責務のルール

### 残すべきテスト

- 仕様を守るシナリオテスト。
: 同時行動、AP境界、視界外攻撃不可、再提出拒否。
- 境界値テスト。
: ターン最終値、視界の境界セル、行動ポイント0/1。

### 削減対象

- 値の写経に近い単純getter/enum判定だけのテスト。
- 空ファイルまたは意味のない重複テスト。

### 原則

- 「実装詳細」ではなく「仕様」をテストする。
- 1つの公開仕様に対して1つ以上の失敗ケースを持つ。

---

## 移行順序（現実装向け）

1. `GridCellsScene` の入力処理を `InputController` へ抽出。
2. 選択/トリガー設定処理を `SelectionService` と `TriggerSettingController` へ抽出。
3. ターン計画/再生を `TurnPlanner` と `TurnReplayController` へ抽出。
4. `ProcessTurnUseCase` を提出処理と解決処理に分離。
5. `Step` `Game` の長手順ロジックをドメインサービス化。
6. テスト棚卸し（低価値削減 + 仕様テスト追加）。

## Done条件

- 主要責務がレイヤーごとに分離され、変更時に触るファイル数が減っている。
- Scene/UseCaseの行数が目標値を満たすか、超える場合は理由が説明できる。
- 仕様テストで回帰が検知できる状態になっている。
