# 単体テスト実装ルール（サンプル案）

## 目的

- リファクタリング後もゲーム仕様を安全に守るため、実装詳細ではなく仕様に紐づく単体テストを整備する。
- 「どのテストを作るか」を先に定義し、機能追加時の品質担保を仕組み化する。

## 適用範囲

- `game-client/game-logics/**`
- `game_server/rust_app/src/application/**`
- `game_server/rust_app/src/domain/**`

## 基本方針

1. 単体テストは公開仕様を検証する。
: private実装や内部変数の値ではなく、入力と出力・副作用で判定する。
2. 1仕様につき「正常系1件 + 異常/境界系1件以上」を用意する。
3. テスト名は振る舞いを表現する。
: `when_xxx_then_yyy` 形式を推奨する。
4. テストは責務分割単位に追従する。
: `InputController` を作ったら `InputController` の単体テストを同PRで追加する。
5. テストデータ生成を共通化する。
: Builder/Factoryで最小データ作成を行い、可読性を保つ。

---

## 優先順位（最初に整備する対象）

1. ターン解決の仕様（サーバー）
2. 視界判定と攻撃制約（サーバー）
3. 入力解釈と行動計画（クライアント）
4. ターン再生の状態遷移（クライアント）

---

## 整備するテスト一覧（作成指針）

### A. Server Application（UseCase/Service）

対象例:

- `ProcessTurnUseCase`
- `TurnSubmissionService`（分割後）
- `TurnResolutionService`（分割後）

作成するテスト:

- 片側提出時は保存のみ行い、解決処理と通知を行わない。
- 両側提出時は解決処理を1回だけ実行する。
- 同一プレイヤーの同一ターン再提出は拒否する。
- リポジトリ更新失敗時にエラーを返し、後続副作用を止める。
- 通知対象は当該2プレイヤーのみである。

観点:

- 呼び出し回数（Mockの `called_times`）
- 返却値（`Ok` / `Err`）
- 早期return時の副作用なし

### B. Server Domain（Game/Step/Visibility）

対象例:

- `Game::turn_start`
- `Step::step_start`
- `Visibility` 関連

作成するテスト:

- 行動ポイント不足時は攻撃/トリガー更新が発生しない。
- bailout状態ユニットは移動/攻撃しない。
- 視界外の敵ユニットがバッグワームを装備していた場合行動結果で秘匿される。
- 視界境界セル（ちょうど範囲端）の可視判定が仕様通りになる。
- 最終ターンで `advance_to_next_turn` が失敗する。

観点:

- 状態遷移の前後差分
- 戦闘生成件数
- 可視セル配列の期待値一致

### C. Client Logic（Controller/Service）

対象例:

- `InputController`（分割後）
- `SelectionService`（分割後）
- `TriggerSettingController`（分割後）
- `TurnPlanner`（分割後）
- `TurnReplayController`（分割後）

作成するテスト:

- ドラッグしきい値未満ではクリック扱い、以上ではドラッグ扱いになる。
- 選択中ユニットのAPに応じて移動可能セル数が変化する。
- トリガー角度更新時、設定タイプに応じた射程/角度が適用される。
- 行動確定後に `Step` が想定フォーマットで記録される。
- 受信Turn再生中は操作入力が抑止される。

観点:

- 状態オブジェクトの変化
- コールバック発火有無
- 描画依存を最小化したロジック単体検証

---

## 境界値ルール

各仕様に対して、最低1つは境界値テストを追加する。

- AP: `0`, `1`, `最大値`
- 距離/射程: `範囲外`, `範囲端`, `範囲内`
- ターン: `開始`, `中間`, `最終`
- 視界: `不可視`, `可視化直後`, `再不可視`

---

## 失敗系ルール

各公開メソッドに対して、最低1つは失敗系を整備する。

- 不正ID
- 不正状態遷移
- 依存先エラー（Repository/WebSocket）
- 重複操作（再提出/二重実行）

---

## テスト構造テンプレート

### Rust（推奨）

- Arrange: テストデータとMockを準備
- Act: 対象メソッドを1回実行
- Assert: 返却値 + 状態 + 副作用を検証

命名例:

- `when_opponent_turn_not_submitted_then_returns_ok_without_resolution`
- `when_action_point_is_zero_then_combat_is_not_generated`

### TypeScript（推奨）

- Arrange: Scene依存をMock化してロジックだけ準備
- Act: 入力イベントまたはメソッド呼び出し
- Assert: 状態変化と外部呼び出しを検証

命名例:

- `when_drag_distance_exceeds_threshold_then_enters_camera_drag_mode`
- `when_all_units_completed_then_turn_is_emitted`

---

## PRでの必須チェック

- [ ] 追加/変更した仕様に対応する単体テストを追加した
- [ ] 正常系だけでなく境界/失敗系を含めた
- [ ] テスト名が仕様を表している
- [ ] Mockの期待が過剰でない（実装詳細に依存しない）
- [ ] ローカル実行で対象テストが安定して通る

## Done条件

- 重要仕様（ターン解決・視界・入力解釈）に対するテストが揃っている。
- リファクタリングでクラス分割した箇所に、対応する新規単体テストが存在する。
- 回帰時に「どの仕様が壊れたか」をテスト名だけで判別できる。
